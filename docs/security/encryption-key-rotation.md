# Encryption & Key Rotation Policy

**Version:** 1.0.0
**Owner:** Security Engineering

## 1. Encryption Standards (implemented)
- **At rest:** AES-256-GCM. See `apps/backend/src/services/security/encryption.service.ts` and `vault.service.ts`.
- **In transit:** TLS 1.2+ enforced via Helmet/HSTS in `apps/backend/src/main.ts`.
- **Payment data:** Tokenized via Stripe/Razorpay; card numbers never stored (see Privacy Policy §Payment Information).

## 2. Key Management
- Application secrets stored in `./secrets/` (gitignored), generated by `infra/scripts/generate-secrets.ps1`.
- Vault-backed secrets via `vault.service.ts` when `VAULT_ENABLED=true`.
- KMS/cloud KMS optional for production key storage.

## 3. Rotation Schedule
| Key type | Rotation | Trigger |
|----------|----------|---------|
| JWT signing secret | 90 days | Scheduled + on staff departure |
| Database credentials | 90 days | Scheduled + on incident |
| Encryption (AES) data key | 180 days | Scheduled |
| API keys (Stripe/Razorpay/Twilio) | On leak or 365 days | Incident or schedule |
| TLS certificates | 60 days before expiry | Automated renew |

## 4. Rotation Procedure
1. Generate new key via secrets script / KMS.
2. Dual-write (support both old + new key) for one rotation window.
3. Re-encrypt or re-sign; verify with `encryption.service.spec.ts` / `vault-*.spec.ts`.
4. Retire old key after grace period; record in `compliance_audits`.

## 5. Break-Glass
Emergency rotation documented in `docs/prod-readiness/*` runbooks; break-glass creds in sealed envelope.
